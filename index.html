Instant undo and redo

Make revisiting an appearance state feel immediate. Confirmed snapshots update the screen while existing server history catches up, one request at a time.

Release blocked · full draft coverage required

Instant undo/redo must cover all draft changes, including mixed visual/content sessions. The current appearance/header-only implementation is incomplete. PR #19181 is draft; the earlier desktop QA results do not establish release readiness.

The intended behavior

Render a previously confirmed state immediately, then synchronize the server cursor in order. This is a bounded snapshot prototype, not a general client sync engine.

What changes for the creator

  • Before: undo/redo waits for a server transaction before showing the restored state.
  • With a warm snapshot: the editor and preview change before the response arrives. Rapid cached moves can continue while requests run in order.
  • On a cache miss: eligibility is decided in the history hook; the existing server path handles navigation. The diagram shows this separate fallback branch.
  • While synchronizing: publish and discard stay blocked until the queue settles.

Desktop QA now verifies eligible title updates before responses delayed by 2,000 ms. Rapid moves and lost-response recovery passed; this is functional evidence, not a production latency benchmark.

Why this shape

Keep server history canonical

Reuse existing undo/redo mutations and cursor semantics. No backend schema or persisted data model changes.

Cache only confirmed states

Retain up to 20 visited appearance/header states in memory per account/session. The entire draft must contain only appearance/header changes; earlier link or social changes force fallback. Both sides need matching preview variables and identical stickers.

Protect the latest visible move

A separate Apollo optimistic layer prevents an older acknowledgement from replacing the creator’s latest requested state. Final confirmation reconciles consumers.

Fall back when uncertain

Cold states, content history, missing preview data, and incompatible states keep server navigation. Refresh loses only the acceleration cache.

Failure recovery

The fixed review finding matters because preview and appearance controls read differently argued fields, even with a shared cache. Reloading the preview alone can leave editor controls stale.

Pilot boundary

Do not expand this to concurrent editing yet. Multi-tab writes or backend coalescing can change snapshot contents without changing their current identity. Broader rollout needs immutable versions or hashes and ordering ordinary edits with history operations.

Rollout order

  1. Verify the deployed QA build with the feature gate off, then on for selected internal testers.
  2. Test warm and cold navigation, rapid undo → redo, failure recovery, account switching, and publish/discard blocking. Include Safari/mobile and remote appearance controls.
  3. After review and QA approval, deploy with curate--instant_undo_redo default-off, then target a small internal cohort.
  4. To stop the pilot, disable the gate. New evaluations stop snapshot navigation and cancel queued moves; an already-sent request settles before reconciliation. Refresh when validating targeting changes.

Gate setup was verified with no pass rules or enrolled testers when prepared. This page does not claim the current console configuration or deployment state.

Decisions

D1
Prototype confirmed snapshots: decided.

Use the existing backend history as truth; accelerate eligible revisits in browser memory.

D2
Opt-in pilot behind a default-off gate: decided.

Require shared editor/preview caching. URL parameters cannot enable the prototype.

D3
Read after ambiguous failure: decided.

Refresh the draft-aware editor query as well as session and preview, guarded by the selected account. Never automatically replay the failed history request.

Still open

Q1
Does the deployed experience feel fast enough across surfaces?

Deployed desktop Chrome QA passed on a clean header-only draft. Safari remains unverified; mobile Design uses separate checkpoint history and stays server-driven.

Lean: require mixed visual/content snapshots, editor and preview agreement, rapid-click correctness, failure recovery, and mobile checkpoint QA before merging.

Q2
How should snapshot identity survive coalescing and concurrent writes?

Current history identity cannot prove that a state’s contents stayed unchanged.

Lean: add a server-issued immutable version or content hash and operation ordering before broad rollout.

Required before release

Complete snapshots must restore link lists and forms, link creation/deletion/reordering, page and collection membership, social links/feeds, stickers, appearance/header fields, and mobile checkpoints. Removing the current eligibility guards alone cannot provide coherent restoration.

General offline sync and multi-tab reconciliation remain separate work. Snapshot identity and write ordering must be reviewed as the implementation expands.

What QA established

  • The flag was working. The original test draft also contained link and social changes, so the whole session was ineligible for snapshots.
  • A clean header-only draft passed. With 2,000 ms added latency, the title field and preview updated before the response, Redo stayed available, and Publish stayed blocked.
  • Rapid moves settled correctly. Redo → undo → redo ran serially on the server and ended at the same title in the editor, preview, and server response.
  • Recovery used reads. Dropping a committed undo response triggered the draft-aware appearance query, preview, and session refresh, without replaying the mutation.
  • Reload stayed canonical. Server history survived; the first cold move waited for the server.
